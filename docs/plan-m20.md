# M20 — iOS 下沉侧栏改为原生根滚动驱动（bridge 8）：实施计划

> 编号按现状取 M20（`docs/plan-m19.md` 是最后一份）。动手时若 `docs/plan-m20.md` 已被占用则顺延，并同步改本文里的 `accept:m20`、`m20-accept.ts`。
> 本文自包含：执行者不需要读过产生它的对话。行号只作提示，动手前按符号重读；仓库里有其他会话在并行改动（main 工作区此刻就有别人未提交的 `CompactThreadHeader.tsx` 等）。

Goal：iOS 26+ 壳里，下沉侧栏的开合由 WKWebView 自己的根 `UIScrollView` 驱动，原生页头与底栏在同一进程里按 `contentOffset` 跟随，删掉 bridge 7 的全部跨合成器对时代码。
Approach：仍是一个 WebView、一份文档。compact 布局在 iOS 原生模式下把文档做成可横向滚动（侧栏 `position: fixed` 垫底，卡片在右侧 in-flow）。执行中启用 C1 和 C2：UIKit 拖动与减速，Swift 决定松手落点、推进程序化开合，并观察 `contentOffset` 同帧更新原生部件。其余平台与旧壳继续走现有 JS 手势和网页页头 / 底栏。原始方案及改动证据见阶段 4 修订。
Rollback point：阶段 1 只存在于不合入的分支上，失败即丢弃，main 不变。阶段 2–4 在 `feat/ios-native-sink` 分支上，合入前丢弃分支即可；合入后回退 = revert 合并提交（没有迁移、没有持久化数据）。任意「新 / 旧壳 × 新 / 旧网页」组合的最坏结果都是网页页头 + 网页底栏（见 R5），所以壳与服务器的发布顺序无约束。

## Context

主人原话：

> 现在回头看看我们前端技术选型对吗，这种跨全端希望所有平台都有优雅体验、需要在部分平台使用原生组件的应用，选这种web套壳方案真的好吗
> 规划进行方案B

前情（`.agent-logs/0277`、`0278`）：Web + Tauri 远程 UI 的方向成立；缺陷在 iOS——网页合成器移动卡片，原生 Liquid Glass 页头叠在 WKWebView 上跟随，两个合成器靠时间对齐。方案 B = 只在 iOS 上反转分工，规则是「谁驱动运动，跟着运动的 UI 就由谁来画」。0278 修正：凡是搬进安装包的导航行为都要和不同版本的自托管服务器协商，所以搬进原生的东西越少越好。

### 已确认的决定（两轮表单，2026-11-20）

| 编号 | 决定 |
|---|---|
| D1 | 架构取 S3：单 WebView，卡片开合 = WKWebView 自带滚动视图的原生滚动，原生页头同进程跟随。第一步先做一轮 CI 验证，不通过就原样回退 |
| D2 | 手势跟系统滚动链：横向可滚的块滚到头后继续右滑会带出侧栏；侧栏打开时在任意位置（含侧栏本身）左滑都能关 |
| D3 | 旧壳（bridge ≤ 7）一律用网页页头 / 底栏；删除 bridge 7 的同步协议，不留兼容代码 |

### 本计划定下的执行层细化（不改变 D1–D3）

| 编号 | 细化 | 理由 | 被否的做法 |
|---|---|---|---|
| E1 | 吸附用根元素 `scroll-snap-type: x mandatory`，程序化开合用 `window.scrollTo`；不写 Swift 滚动代理与 CADisplayLink | WebKit 在 UI 进程里自己算吸附目标（`WKWebViewIOS.mm` 的 `scrollViewWillEndDragging` 就是为 CSS snapping 调目标）；运动参数留在网页、随服务器发（0278）；Swift 新增降到一个观察器；Chromium 里已跑通原型（见下） | 表单里展示的「Swift 代理吸附 + CADisplayLink 插值」：盲写 Swift 更多，且与 WebKit 的 resnap 互相改 offset。降为预案 C1 / C2 |
| E2 | 网页从自己的 `window.scrollX` 得知开合（带内），不加 native → page 的状态事件 | 遮挡探测读的就是这份布局；事件通道会与布局状态有先后差 | 原生静止事件。降为预案 C4 |
| E3 | 握手命令 `host_sink_set {on}`；壳在它生效前拒绝非空的 `host_tab_bar_set` / `host_header_set` | 旧网页（bridge 7 语义）连到新壳时必须在 `set` 这一步被拒，才会走它已有的「set 被拒 → 网页页头 / 底栏」路径 | 给 spec 加必填字段（人为字段）；改命令名（无状态但纯为错开版本） |
| E4 | 初始落位与窗口尺寸变化后的落位由网页 `scrollTo({behavior: "instant"})` 做 | 与宽布局同一次提交，没有先露出侧栏的一帧 | 原生 KVO `contentSize` 后设 offset |

### 已有证据

- 已读 WebKit `main` 源码：`WKScrollViewDelegateForwarder` 先调内部代理再调外部代理；`_updateScrollViewForTransaction` 只在主框架可滚或缩放时启用 pan；`_scrollToContentScrollPosition:…animated:` 走 `[_scrollView setContentOffset:animated:]`。
- wry 0.57.2 iOS：对滚动视图只做了 `setBounces(false)`；WebView 是 tao 根视图的普通子视图。
- 2026-11-20 在本机 Chromium（393×852、触摸、DPR 3）跑过一次性原型，CSS 结构与步骤 3.2 相同：

| 操作 | 结果 |
|---|---|
| 加载；`scrollTo(W, instant)` | 可滚范围 = 320 = 侧栏宽；纵向范围 0；侧栏左缘 0，卡片左缘 0 |
| `scrollTo(0 / W, smooth)` | 停在 0 / 320；卡片内 `position: fixed` 的元素随卡片走（卡片保留 `translate: 0px 0`） |
| 程序化滚到 40% / 70% | 自动吸附到 0 / 320 |
| 慢拖 30% / 70%；快甩 25% | 回关闭 / 打开；打开 |
| 打开态在卡片条、在固定侧栏上左滑 | 都关闭 |
| 内层纵向滚动；斜向（50, −300） | 根没有收到任何 scroll 事件 |
| `pre` 内横滑；已在最左再右滑 | 只滚 `pre`；带出侧栏（= D2） |
| 打开态对卡片内元素 `scrollIntoView` / 不带 `preventScroll` 的 `focus()` | **根被滚回关闭**（步骤 3.2 的守卫针对它） |
| 视口变窄到 320 | 仍吸附在关闭位（新的 max） |

  这些只说明网页侧机制成立；iOS 上的 UIScrollView 行为由阶段 1 验证。

## 需求（每条都能由第三方判断真假）

- R1 iOS 26+、壳 bridge ≥ 8、compact 布局：手指横向拖动时卡片 1:1 跟手，松手后停在打开位或关闭位之一。判定：端到端里按住拖到侧栏宽的 55% 时卡片左缘在该位置（像素）；松手后无障碍树显示侧栏可交互。

## Assumptions

- A1 WKWebView 的根可以横向滚动，且 `position: fixed` 的侧栏、非不透明 WebView 下面的原生底栏在手指拖动的每一帧都留在原地；不触发缩小适配，不出现纵向滚动范围。受影响：步骤 2.1–4.3 全部。由步骤 1.1 的 S1、S2、S5、S9 判定；为假 → 回退 F。
- A2 根元素的 CSS scroll-snap 在 WKWebView 的 UIScrollView 上生效。受影响：3.2。S4 判定；为假 → 预案 C1。
- A3 根的 `scrollTo({behavior: "smooth"})` 能到位。受影响：3.2。S2、S3 判定；为假 → 预案 C2。
- A4 软键盘弹出与收起不改变根的横向位置。受影响：3.2。S8 判定；为假 → 预案 C3。
- A5 内层纵向滚动不带动根。受影响：3.2。S6 判定；为假 → 预案 C5。
- A6 页面的 `scrollX` 在静止时等于 0 或 max，拖动中与手指位置一致。受影响：3.1、3.2。S1–S5 判定；为假 → 预案 C4。
- A7 iOS 壳的安装量只有 TestFlight 内部测试，bridge 7 壳退回网页页头 / 底栏可以接受（D3）。受影响：2.1、3.1。
- A8 D2 的含义按上表理解（表单选项原文在会话归档里只剩后半句）。受影响：3.2 不加 `overscroll-behavior` / `touch-action` 拦截。为假 → 3.2 增加对应 CSS，不影响其它步骤。

## 阶段 4 修订：启用 C1，保留 C2

- 阶段 1 证明了 CSS 吸附能承接手指拖动，但阶段 4 发现它不能与程序化开合可靠共存。相同提交 `4c6ced6` 的两次 iOS 取样一红一绿：run `44751816572` 重跑在 `final` 失败，原生关到 `x=320` 后出现 `move 320→0`，再由网页请求一步落回；run `44756314532` 没有回弹。WebKit `safari-7622-branch` 的 `WKWebViewIOS.mm`（`_updateVisibleContentRects`）会调度一步回到旧吸附点，而主框架的吸附索引在手指松手时更新。失败的原生调用栈形状与这条路径吻合。网页切换 `scroll-snap-type` 不等待 UI 进程应用，恢复后还可能读到旧索引，因此不保留这条吸附路径。
- 步骤 2.2 与 3.2 改用 C1：`SinkFollow` 的外部 `UIScrollViewDelegate` 只改横向落点，UIKit 仍处理拖动与减速，WebKit 仍处理内部代理。快甩按方向（`|v| > 0.3 pt/ms`），其余取近端。删根 CSS 吸附与网页切换吸附的逻辑，保留 C2 的逐帧程序化开合、原生同帧跟随、历史恢复守卫与 bridge 8 契约。Chromium 浏览器脚本只代做 iOS 宿主的松手落点；实际落点由模拟器的 `drag`、`h-drag` 和 `final` 验证。
- 步骤 4.1 须从对应 PR 运行下载 `ios-screenshot`，确认 `e2e/.complete` 存在。run `44766975907` 下载后有 `header/.complete` 与 `e2e/e2e-h-drag.png`，端到端最后的 `appicon.set（default）` 超时，下载产物没有 `e2e/.complete`；该次不算通过。
- 补齐回弹断言：C1 的网页守卫能直接用 `scrollTo` 拉回，不会再留下原生 `jump` / `start`。`no_bounce` 也检查到位后从终点离开超过 1pt 的 `move`。旧失败 run `44751816572` 的 `events.jsonl:26–27` 去掉后续 `jump` 后仍被拒绝；C1 成功 run `44774441275` 的 `open`、`closed`、`final` 轨迹通过同一谓词。
- 初始化关闭基线要等原生根滚动到位再连拍。失败 run `44785123524` 中底栏先接管，根过了约 22 秒才滚到关闭端；过早采的 `closed0` 实际仍露出底栏，不能作为像素对照。
